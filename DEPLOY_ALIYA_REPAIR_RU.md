# Китобхона + Алия — пакет исправлений (12.11.2026)

## Состав и назначение

Это **дельта-пакет** для корня репозитория `sharipovip/kitobkhona`, а не новый APK. Он содержит фронтенд чата/инструментов, передачу контекста из читалки, исправления адаптивности/кэша и проверки. Устанавливайте файлы, сохраняя пути из архива.

## Что исправлено

- Основной чат теперь использует реальный контракт шлюза: `POST /v1/chat`, `reasoning_mode`, увеличенный тайм-аут, ограниченные повторы при временном отказе провайдера и понятное сообщение вместо выдуманного ответа.
- Удалён ложный локальный «ответ» и демонстрационная картинка `picsum.photos`: при недоступности AI интерфейс честно сообщает, что именно недоступно.
- Исправлены пути и схемы запросов:
  - изображение/скан: `POST /v1/vision` с `image_base64`, `prompt`, `system`;
  - генерация изображений: `POST /v1/image` и чтение `image_base64`;
  - PDF: `POST /v1/document/generate`.
- Реализованы отсутствовавшие методы `generateLessonPlan` и `generateTest`. Языковой выбор плана: тоҷикӣ — **Нақшаи дарс**, русский — **Поурочный план-конспект**.
- Тесты создаются по выбранным формату, классу, теме и числу вопросов. Ученическая версия не раскрывает ответы; отдельный DOCX-ключ для учителя помечает правильные варианты `[✓]`. Для DOCX и PDF есть отдельный экспорт.
- Помощник диктанта/баён учитывает класс, четверть, тему и сложность; диапазон слов в запросе обозначен как ориентировочный, не как обязательная государственная норма.
- В чате работают история на этом устройстве, переключатель глубины, фото-вложение и обработка ошибок; заметки выводятся безопасно и поддерживают поиск/удаление.
- В читалке исправлена инициализация помощника после построения DOM, убраны шаблонные фальшивые ответы. Текстовый PDF передаёт извлечённый текст; скан — уменьшенное изображение страницы в Vision/OCR. Результат можно продолжить в полном чате, сохранить в заметки и экспортировать в DOCX/PDF.
- Включён новый номер кэша Service Worker, чтобы установленная PWA не продолжала использовать старые файлы.
- Общий слой desktop-стилей подключён ещё к `chat.html` и `maorif-books.html`.

## Проверки

Запустить в корне проекта:

```bash
node tests/aliya-smoke.js
python tests/check_aliya_html.py
```

Smoke-тест проверяет форматы запросов, OCR, создание DOCX-пакета, изоляцию ключа от ученического теста, PDF-экспорт и точный фирменный блок. DOCX дополнительно проверены через `unzip -t`.

Во время проверки публичный шлюз отвечал `200` на `/health`, а простой вопрос через `/v1/chat` успешно получил ответ. Однако последующие реальные запросы временами возвращали `chat_providers_unavailable`. Глубокая диагностика шлюза показала среди причин `403 no_access_to_model_or_provider` у ряда HF-моделей, `429 rate_limited` у Gemini и `402 insufficient_credits` у некоторых платных провайдеров.

**Это не исправляется изменением HTML или архивом:** владелец Space должен проверить/обновить доступ Hugging Face, лимиты Gemini и баланс/доступность платных API-провайдеров. Секреты, токены и производственный сервер здесь не изменялись. Клиент после этих исправлений не маскирует такой сбой и сообщает причину.

## Ограничения этой поставки

- В клоне GitHub нет исходного Android/Gradle-проекта: здесь лежит веб/PWA-код. Поэтому APK не пересобирался и нативные методы `AndroidBridge` физически не проверялись; фронтенд вызывает их, если они предоставлены установленным приложением, и иначе использует скачивание браузера.
- Полный файл Google Drive `Алия.zip` (66 МБ) доступен по метаданным, но прямое скачивание из рабочей среды перенаправлялось на Google Sign-in. Поэтому сверить исходники APK из этого архива не удалось. Небольшой `kitobkhona_aliya_update_v1.zip` был прочитан: его веб-файлы совпадают с GitHub на момент аудита; в нём дополнительно находился отдельный `aliya_cloud_gateway/app.py`.
- Для изменений шлюза нужны исходники Space и его секреты/панель провайдеров; этот пакет не содержит секретов и не выполняет удалённый деплой.


## Windows-сборка

Существующий workflow заменён на воспроизводимую Electron-сборку: локальный безопасный HTTP-сервер обслуживает статические файлы, Electron renderer работает без Node-доступа и с включённой изоляцией контекста. Workflow на Windows публикует сборку как Actions artifact; при push-теге вида `v*` дополнительно прикладывает `Kitobkhona-Setup.exe` к GitHub Release. Локально сборку можно запустить командами `npm install` и `npm run dist:win`. Windows-установщик в этой среде не запускался и должен быть проверен GitHub Actions/на Windows перед публикацией.

## Какие серверные действия остались владельцу

1. В Hugging Face Space открыть provider diagnostics и восстановить ключи/доступы/баланс для каналов, используемых именно чатом (наличие переменной окружения само по себе не означает успешный ответ).
2. Повторить реальный `POST /v1/chat` после исправления, а не ограничиваться `GET /health`.
3. После успешного запуска Actions на Windows добавить тег версии (`v3.1.0` или следующий) — workflow опубликует установщик в Release; до этого ссылка Download может не иметь опубликованного файла.
4. На реальном APK проверить сохранение документа через нативный `AndroidBridge.saveFile`; если мост отсутствует в установленной версии, браузерный вариант остаётся резервом.
