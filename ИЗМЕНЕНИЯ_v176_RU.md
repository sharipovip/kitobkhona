# ИЗМЕНЕНИЯ v176 — свободный зум книги + Алия в Reader с экспортом в Word/PDF

Ветка: `arena/90cba743-kitobkhona`. Предыдущая часть (свободный зум, тема в одно
нажатие, экспорт ответов Алии) вошла в состав `main` через PR #5; этот выпуск
добивает то, что осталось: чистит мёртвую копию приложения, поднимает версии
ассетов и **закрывает последний непроверенный путь — реальный экспорт в PDF**.

## 1. Удалена мёртвая копия приложения (`app/`)

### Причина

В репозитории лежала папка `app/` — старая копия приложения:

| Файл | Размер | Состояние |
|---|---|---|
| `app/reader.html` | 102 КБ | старая версия читалки |
| `app/sw.js` | 23 КБ | старый Service Worker (без `dovtalab/`) |
| `app/aliya/index.html` | 106 КБ | старая версия главной Алии |
| `app/aliya/aliya-ui.css` | 55 КБ | старые стили Алии |

На неё **никто не ссылался**: ни одна страница, ни один скрипт, ни точка входа
Electron. В `precache` Service Worker её не было, отдельного `manifest` и
`electron`точки входа у неё тоже нет. Это подтверждается сравнением с
корневыми файлами: корневые версии содержат **всё то же самое плюс** более поздние
исправления (эмблема в «думаю», скрытие `.msg-top`, записи `dovtalab/` в
precache, `readerCurlBusy`, `__kkToggleBars`).

Опасность была не в размере, а в том, что в `app/reader.html` оставались **старые
баги** — `Z_MAX = 2.2` и переключатель темы через два нажатия. Именно на этот
файл легко было наступить при правке (так случилось в предыдущей сессии).

### Решение

Папка `app/` удалена. Запись добавлена в `DELETE_FILES_RU.txt` — так же, как
репозиторий уже поступал с мёртвым `chat старй.html`. Актуальные файлы остались
в корне: `reader.html`, `sw.js`, `aliya/index.html`, `aliya/aliya-ui.css`.

Регрессия добавлена в `tests/check_aliya_html.py`: папка `app/` не должна
вернуться, и ни одна страница не должна на неё ссылаться.

## 2. Версии ассетов приведены в соответствие с кешем Service Worker

### Причина

Service Worker кеширует `.js`/`.css` по ключу **без учёта query-строки**
(`cache.match(request, { ignoreSearch: true })`). Значит `aliya-tasks.js?v=175`
и `aliya-tasks.js?v=161` и `aliya-tasks.js?v=176` — это **один и тот же** ключ
кеша. Префикс `?v=` не «сбивает» кеш; единственное, что реально обновляет ассет,
— новый `CACHE_NAME`: при `activate` старые кеши удаляются по шаблону
`/^kitobkhona-v\d+[-\w]*$/`, а новый заполняется заново при `install`.

А я менял `aliya/aliya-tasks.js` (режим `append` + стиль `.at-ans-wrap`) и версию
не поднял — часть пользователей долго получала бы старый файл из кеша.

### Решение

- `CACHE_NAME`: `kitobkhona-v175-aliya-reader-fixes` → **`kitobkhona-v176-aliya-reader-zoom-theme`**.
- `aliya-tasks.js?v=175` → `?v=176` в `reader.html` и `aliya/index.html`.
- `aliya-tasks.js?v=161` → `?v=176` в `aliya/reader-aliya.html`.

Регрессия в `tests/check_aliya_html.py`: версия в `?v=` обязана совпадать с
версией в `CACHE_NAME`, иначе сообщение прямо говорит, что пользователи
получат старый файл из кеша.

## 3. Экспорт Алии в PDF наконец проверен по-настоящему

### Причина

До сих пор PDF-проверка ограничивалась утверждением «не зависает»: в песочнице
нет исходящей сети, поэтому локальные библиотеки не загружались и проверка
возвращала читаемую сетевую ошибку. Реальный PDF-файл не получался **никогда**.

При этом код оказался полностью локальным и вовсе не зависящим от CDN:
`aliya-pdf.js` грузит `assets/libs/pdf-lib.min.js`, `assets/libs/fontkit.umd.min.js`
и четыре шрифта из `assets/fonts/` — всё это есть в репозитории, и путь через
`scriptBase()` резолвится верно.

### Решение

`tests/reader-aliya-pdf-runtime.js` загружает **настоящие** библиотеки и
**настоящие** шрифты и прогоняет реальный `aliya-pdf.js`. Проверяется:

- библиотеки и шрифты грузятся из локальных ассетов;
- на выходе `Blob` с типом `application/pdf`;
- файл начинается с `%%PDF-` и заканчивается `%%EOF`;
- файл **разбирается обратно** через `pdf-lib`: есть страницы, размер A4
  (595.28 pt), заголовок документа сохранён.

То есть PDF-экспорт теперь подтверждён так же надёжно, как Word.

### Тонкость стенда (важно для будущих тестов)

pdf-lib проверяет свои аргументы через `instanceof` относительно классов
**своего** realm. Поэтому:

- в VM-контекст нельзя передавать встроенные объекты внешнего realm
  (`Promise`, `Array`, `Object`...) — `addPage()` начнёт отвергать корректный
  размер страницы с обманчивым сообщением «type NaN»;
- `window` внутри контекста должен указывать на **глобальный объект контекста**;
- байты шрифтов и готового PDF нужно копировать в realm контекста.

Это особенность стенда, а не приложения: в браузере всё работает в одном realm.
